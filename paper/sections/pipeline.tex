The released scripts implement five stages. S1 describes the visible actions in each video as a generated transcript. S2 summarizes each worker's generated transcripts. S3 combines the worker summaries into a factory report and shared label lists. S4 extracts events from each original generated transcript using those lists and the compact worker entry from the S3 report. S5 merges the resulting CSVs. Figure~\ref{fig:dependency} shows these dependencies. Reports and logs share evidence, so their agreement is not independent validation.

Adaptation takes place in the context and vocabulary, while the foundation-model parameters remain fixed. Each available factory corpus contributes to its own label lists through S2 and S3, and S4 then uses those lists to label recordings from that corpus. The six-factory assessment therefore applies the same construction procedure to six separately induced representations. It is a retrospective use of the available material, not an evaluation of a fixed vocabulary on a previously unseen factory. Prompts also supply analyst choices about operational relevance and granularity.

\subsection{Vocabulary construction as event abstraction}
\label{sec:abstraction}
Event abstraction concerns the level at which observations represent process behavior~\cite{vanZelst2021abstraction}. Table~\ref{tab:abstraction} separates three decisions in our implementation. Constructing a reusable class and assigning an event to it are different tasks: a missing concept and a mistaken assignment require different checks. The process list supplies a second label dimension, with no enforced parent-child relation to the activity list.

\subsection{Execution units and failure behavior}
Table~\ref{tab:stages} states the input, output, and failure behavior for each execution unit. The algorithm below gives their dependency order.

\begin{lstlisting}[float=!t,caption={Algorithm 1: implemented dependency order. API retries surround requests; this pseudocode does not add windowing or new validation.},label={alg:pipeline}]
for each selected factory f:
    for each available video v:
        T[v] = reuse existing transcript or S1(video[v], prompt1)
    for each worker w:
        B = concatenate all T[v] for w, without filenames
        R[w] = reuse existing summary or S2(B, prompt2)
    F[f] = reuse existing report or S3(all R[w] for f, prompt3)
    A, P, worker_context = parse the required sections of F[f]
    for each transcript T[v]:
        context = T[v] + A + P + worker_context[w]
        E[v] = reuse CSV or normalize(S4(context, prompt4))
    for each worker w:
        offset = 0
        for each CSV v in sorted filename order:
            append E[v] shifted by offset; keep local offsets
            if E[v] is nonempty: offset += max end(E[v])
    concatenate worker logs into the factory log
\end{lstlisting}

S1 asks for a new timestamped entry when an action, object, location, or interaction changes. It asks for repeated stable work to be summarized once and for uncertainty to be stated briefly. These are instructions to the model. S1 does not check whether each visible change was narrated or whether the timestamps match the video.

S2 and S3 compress large text bundles into summaries. This makes factory-wide vocabulary induction possible, but uncommon actions can be lost. The implementation does not automatically split long requests into windows, reconcile separate summaries, or check coverage against all generated transcript spans. S4 partly bypasses this compression by reading each original generated transcript, although it must still use the induced vocabularies.

S4 requests a strict JSON schema with estimated start and end times, activity, and process. Its local parser can also accept a list, strip code fences, recognize fallback time keys, and parse two-component offsets or numeric seconds. It normalizes label case and surrounding quotes, checks membership, rejects end-before-start intervals, and sorts rows by start, end, activity, and process. It allows zero-duration events and overlaps. It does not check video bounds, full temporal coverage, the truth of an activity, or compatibility between the activity and process. The archive contains CSV outputs, not the original S4 JSON responses.

S1 to S3 default to \texttt{gemini-3.1-pro-preview}; S4 defaults to \texttt{gpt-5.4}, requests high reasoning effort, and permits up to 100 concurrent extraction tasks. These are recoverable code settings. Per-request execution records are unavailable. No temperature, token limit, seed, cost, or runtime is inferred from missing records. Appendix~\ref{supp-app:repro} of the Additional Material specifies the distinction between code defaults and historical execution evidence.

\subsection{Design choices and tradeoffs}
Table~\ref{tab:tradeoffs} summarizes the design choices and alternatives. Repeated cycles deserve particular care. If ten cycles become one narrated interval and one event, the event count decreases and the directly-follows relation loses nine possible repetitions. A longer event can represent more repetitions, slower work, or more aggressive compression. The logs alone do not distinguish these explanations. The text interface makes this decision inspectable, but does not recover details omitted from the generated transcript.
