\section{Pipeline and Design Rationale}
\label{sec:pipeline}
The released scripts implement five stages. S1 uses video and a transcription prompt. S2 combines a worker's transcripts. S3 combines a factory's worker summaries. S4 uses the original transcript again, together with the factory vocabularies and the compact worker entry from the S3 report. S5 merges the resulting CSVs. Figure~\ref{fig:dependency} shows these dependencies. Reports and logs share evidence, so their agreement is not independent validation.

\caption{Stage specification from scripts 01 to 05. A nonempty text output is not a validation of its factual content.}

\begin{tabularx}{\linewidth}{@{}lLLL@{}}\toprule

\begin{lstlisting}[caption={Algorithm 1: implemented dependency order. API retries surround requests; this pseudocode does not add windowing or new validation.},label={alg:pipeline}]
for each selected factory f:
    for each available video v:
        T[v] = reuse existing transcript or S1(video[v], prompt1)
    for each worker w:
        B = concatenate all T[v] for w, without filenames
        R[w] = reuse existing summary or S2(B, prompt2)
    F[f] = reuse existing report or S3(all R[w] for f, prompt3)
    A, P, worker_context = parse the required sections of F[f]
    for each transcript T[v]:
        context = T[v] + A + P + worker_context[w]
        E[v] = reuse CSV or normalize(S4(context, prompt4))
    for each worker w:
        offset = 0
        for each CSV v in sorted filename order:
            append E[v] shifted by offset; keep local offsets
            if E[v] is nonempty: offset += max end(E[v])
    concatenate worker logs into the factory log
\end{lstlisting}

S1 asks for a new timestamped entry when an action, object, location, or interaction changes. It asks for repeated stable work to be summarized once and for uncertainty to be stated briefly. These are instructions to the model. S1 does not check whether each visible change was narrated or whether the timestamps match the video.

S2 and S3 compress large text bundles into summaries. This makes factory-wide vocabulary induction possible, but uncommon actions can be lost. The implementation does not automatically split long requests into windows, reconcile separate summaries, or check coverage against all transcript spans. S4 partly bypasses this compression by reading each original transcript, although it must still use the induced vocabularies.

S4 requests a strict JSON schema with estimated start and end times, activity, and process. Its local parser can also accept a list, strip code fences, recognize fallback time keys, and parse two-component offsets or numeric seconds. It normalizes label case and surrounding quotes, checks membership, rejects end-before-start intervals, and sorts rows by start, end, activity, and process. It allows zero-duration events and overlaps. It does not check video bounds, full temporal coverage, the truth of an activity, or compatibility between the activity and process. The archive contains CSV outputs, not the original S4 JSON responses.

S1 to S3 default to \texttt{gemini-3.1-pro-preview}; S4 defaults to \texttt{gpt-5.4}, requests high reasoning effort, and permits up to 100 concurrent extraction tasks. These are recoverable code settings. The existing manuscript identifies the corresponding model families, but per-request execution records are unavailable. No temperature, token limit, seed, cost, or runtime is inferred from missing records. Appendix~\ref{app:repro} specifies the distinction between code defaults and historical execution evidence.

``Automated extraction'' means that no task-specific training or manual input annotation is required by the extraction stages. It does not mean that the complete study is free of human judgment. One author conducted the archived transcript audit, and the operational-category map reflects author choices. ``Constrained'' refers to the separate permitted label lists. ``Validated'' is used only with a named check, never as a general claim of visual accuracy.

\subsection{Design choices and tradeoffs}
\begin{table}[htbp]
\caption{Design rationale and conceptual alternatives. No alternative in the last column was experimentally compared here.}\label{tab:tradeoffs}\footnotesize
\begin{tabularx}{\linewidth}{@{}p{0.19\linewidth}LLL@{}}\toprule
Choice & Intended benefit & Limitation & Possible alternative \\\midrule
Video-to-text intermediate & Readable evidence; reuse for different analyses & Visual errors become shared textual evidence & Direct video-to-events, with stronger visual provenance \\
Worker summaries & Compact factory-level context & Rare behavior and recording identity may be lost & Window summaries with explicit source references \\
Factory vocabularies & Concrete local labels across workers & Different factories use different abstractions & Global concepts with local extensions \\
Closed labels & Prevent out-of-list output & Closest allowed label may still be wrong & Open labels followed by review and reconciliation \\
Change-point narration & Compact description of stable behavior & Boundary detail and repeated cycles can disappear & Finer segments with explicit repetition counts \\
Interval events & Preserve approximate episode duration & Row counts do not equal production volume & Object-linked cycle records, when supported \\
\bottomrule\end{tabularx}
\end{table}

Repeated cycles deserve particular care. If ten cycles become one narrated interval and one event, the event count decreases and the directly-follows relation loses nine possible repetitions. A longer event can represent more repetitions, slower work, or more aggressive compression. The logs alone do not distinguish these explanations. The text interface makes this decision inspectable, but does not recover details omitted during transcription.
