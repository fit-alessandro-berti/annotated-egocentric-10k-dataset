\section{Problem Definition}
\label{sec:problem}
Let $F$ be a set of factories, $W_f$ the worker identifiers associated with factory $f$, and $V_w$ the recordings associated with worker $w$. Each video $v$ has an underlying duration $D_v$, which need not be available in the derived archive. A transcript $T_v$ is an ordered collection of entries $(s_i,e_i,x_i)$, where $x_i$ describes the interval from $s_i$ to $e_i$. These endpoints and descriptions are model outputs. They are not independent annotations of the source video.

For each factory, the pipeline induces an activity vocabulary $A_f$ and a process vocabulary $P_f$. An interval event is
\begin{equation}
 e=(v,w,f,t_s,t_e,a,p), \qquad a\in A_f,\quad p\in P_f.
\end{equation}
The tuple makes provenance explicit: the CSV's path identifies $v$, while $w$ and $f$ are stored in each row. The estimated endpoints $t_s,t_e$ are relative to the video. A case function $\kappa:E\rightarrow K$ groups events into traces; it is an analytical choice. The construction problem is to derive $E$, $A_f$, and $P_f$ from the videos while retaining enough source information to inspect and interpret the result.

An event represents an operational episode. One episode may summarize many repeated actions, and several events may divide a single narrated interval. It need not be one item, one production cycle, or one complete process instance. Desirable properties include faithful descriptions, meaningful boundaries, appropriate labels, and sufficient coverage. The implementation enforces only a subset: parseable offsets, end not before start, required values, and membership in the separate vocabularies. Section~\ref{sec:guarantees} distinguishes these checks from intended properties.

\subsection{Activity, process context, and analytical category}
An \emph{activity} answers what action is performed. A \emph{process context} identifies the broader operation to which the extractor assigns it. An \emph{operational category} answers how an analyst groups the action or context for a particular question. These concepts are separate. The implementation checks $a\in A_f$ and $p\in P_f$ independently. It does not enforce a compatibility relation $H_f\subseteq A_f\times P_f$ or a process-to-activity hierarchy.

The current time analysis uses $g_f(p)$, not an activity-based mapping. Thus, transport within surface finishing can receive the category assigned to finishing. Figure~\ref{fig:category} gives an exact released example. An explicit compatibility relation or a category rule using $(a,p)$ could improve future analyses, but neither was enforced in this extraction. Reclassifying all activities would define a different analysis and is not part of the present revision.
